## Hippocampus updates happen inline, not at session-end

Update the knowledge base (the lobes in `docs/`) **as work happens during a session** — not as a final batch step.

**Why this matters:** Sessions end and context clears before the "now update the docs" step happens. Deferred updates get missed. The knowledge base IS the institutional memory; if a decision isn't recorded, future sessions don't know it was made. The recurring failure mode: finishing a session and clearing context before the durable insight is written down.

## The hot + warm tiers must stay true to reality (this is the point)

The knowledge base's core job is to distill and tier context for efficient retrieval. The **hot tier** (the lobes: the spine doc — MODEL — read in full every session, plus the always-indexed lobes PLAN / QUESTIONS / PEOPLE) and the **warm tier** (`workstreams/*`: frontmatter always indexed, body on-demand and discoverable) are working memory. They must reflect the **true current state** of the work and any context a future session will need. Everything else is cold: `proposals/` (deliverables, not per-doc indexed — a fresh session doesn't know a proposal exists unless a warm/hot doc points to it), DECISIONS (audit), INTEL (evidence), WORKLOG (transient oplog, ~3-day rolling window; older days archived to `worklog-archive/`). **Cold and transient tiers do NOT substitute for the hot/warm tier being current.** A conclusion that lives only in a proposal + WORKLOG is on a path to invisibility.

**The trigger is a change in what is true OR in our understanding of it — not a file being edited.** It fires on both: reality moving (a decision, a live-source finding, an external input like an email or meeting, a shifted plan) AND understanding deepening or correcting even when nothing external changed (a newly-grasped mechanism, a synthesis, a reframed model). The second kind is easy to miss precisely because the world didn't move: reading a vendor's code samples doesn't change reality, but it corrects our understanding of a seam, and the hot/warm tier still has to move to match. Most changes do not originate in a doc edit at all. After any turn that changes what is true, or what we understand, or that surfaces context a future session will need, make the relevant hot/warm doc (and its frontmatter, if the essence shifted) reflect it — independent of whether any proposal, PR, or artifact was touched. Appending to WORKLOG or editing a cold proposal does **not** discharge this; only the hot/warm tier reflecting current truth-and-understanding does.

**Per-turn self-check:** *Is the hot/warm tier now true? Is anything a future session needs living only somewhere cold or transient?* If yes, promote it now. Keep the hot lobes tight (they load every session): promote the distilled conclusion + a pointer to the warm/cold detail, not the raw detail. A major workstream that exists in reality but has no entry in the master-plan lobe, a settled decision the spine still calls "leaning", a frontmatter summary that names a superseded fact — these are the failure mode, and they are worse than a missing WORKLOG line because every future session trusts the stale hot/warm tier first.

The per-doc routing below is how this principle plays out by tier.

**When to update each doc:**

- **DECISIONS.md** — Immediately after locking in a non-trivial decision. Append a dated entry with: what was decided, why, what it supersedes (if anything), and downstream implications. **The bar: a load-bearing, revisitable architectural choice you would later open DECISIONS to understand — "why is the system shaped this way?"** Apply the refer-back test before writing: *would anyone ever come back to this entry?* If not, it is not a decision, it is oplog, and it bloats a COLD doc whose whole value is signal. **NOT DECISIONS (common miscategorizations):** (1) **executing a prior decision** — building the thing already decided is work, not a new decision → git/PR/On-Deck; (2) **sequencing/scoping calls** ("build it now vs. defer", "do X before Y") — they evaporate once done, no one reopens them → On-Deck at most; (3) **reference facts / SDK gotchas / API shapes** — not decisions → a code comment next to the thing they explain; (4) **"why is this code structured this way"** — belongs in the code's docstring where a maintainer will actually see it, not a doc they won't think to open; (5) **incident/bug fixes** → a tracker ticket. A genuine new entry is rare: most sessions execute prior decisions and record state (On-Deck) + work (git/PR), not new architecture. When in doubt, leave it out — a missing oplog entry costs nothing; a doc full of one-offs no one revisits costs the doc its usefulness.
- **INTEL.md** — As new intel surfaces *from an external source* (a live API/console finding, a constraint, config state, a meeting or conversation). Brief, factual, timestamped, source named. **INTEL is an intake buffer + evidence ledger, not a session changelog.** Test before writing: *did I learn this from the world, or did I just do it?* A recap of edits you made is not intel — you did it, you didn't learn it, and the lobes + your tracker + git already record it. When an entry's durable conclusion is synthesized into a lobe, mark it `✅ PROCESSED — Processed into: [targets]`; if that line would be empty, the entry doesn't belong here. Lifecycle is status-driven, not age-driven: RAW → synthesize; PROCESSED + cited by a lobe → keep; PROCESSED + uncited → archive, never delete.
- **WORKLOG.md** — The "what I did today" session changelog that INTEL and DECISIONS deliberately exclude finally has a home here. Append terse, outcome-focused lines as work completes: ops actions (deploys, config changes, migrations), investigations and their dead-ends, comms sent, decisions still in flight — the connective tissue git commits and tracker tickets don't capture, so standup/status notes read rich instead of thin. It's safe because it's read-on-demand-only (never loaded at session start, the property that sinks a naive oplog) and bounded to a rolling ~3-day window (`.claude/hooks/hippo-worklog-prune.py`). **What rolls off is archived, not discarded** — it lands in `<kb>/worklog-archive/<ISO-year>-W<week>.md` and is the source for timesheets and monthly hours logs, since it is the only record of what was *done* rather than what was committed. Write with that second reader in mind: name the thing worked on and the outcome, not just the fact of activity. This does NOT relax the rules above: a durable *fact/decision/model-shift* still routes to its proper lobe. WORKLOG is the transient oplog; the lobes are the memory.
  - **Definition of done:** a milestone is not finished until its WORKLOG line exists **in the same turn**. Milestones = a PR opened/merged, a deploy, a commit, a tracker comment/status change, a shared deliverable written (`comms/`, `proposals/`), or an advisory piece landing (a review, a reply, a decision). Do NOT defer the append to session end — a `/clear` before then loses it. This is enforced, not just asked: `hippo-worklog-nudge.py` (PostToolUse) fires a reminder at each milestone action, and `hippo-worklog-precompact.py` (PreCompact) reminds before a `/compact`. Note the hooks *remind*; they can't write, and `/clear` fires SessionEnd (whose output never returns to the model), so the append is still yours and the discipline is to keep the log current, not to rely on a last-second nag.
  - **Upsert, don't sprawl.** Within a day-section, fold new detail into the existing entry for that work-thread rather than appending a fresh fragment each time a milestone fires. Broad triggers stay useful precisely because the log stays one coherent block per day, newest day on top — not a pile of one-line stubs.
- **PLAN.md** — When a workstream visibly moves: project/issue created, milestone hit, blocker discovered, deadline shifted.
- **MODEL.md** — When the structural mental model itself shifts (a new pattern, a clarified relationship). Update sparingly; read at every session start, so keep it tight. Finer-grained detail (volumes, evidence, specifics) drops to the relevant workstream doc, which the spine can point to. **Corollary — do not narrate an in-flight operation in the spine.** MODEL states what is *true of the system*; an operation in progress (a migration mid-flight, a long backfill draining) changes daily and will rot silently, because nothing forces a re-read of the spine when it finishes. Record the operation in its workstream doc and let the spine carry only the settled world-state it leaves behind. A stale claim here is the most expensive kind you can have: it is read in full, and trusted first, every single session.
- **QUESTIONS.md** — When new open questions emerge or existing ones get answered.
- **TASKS.md § On Deck** — the next-session slate. **It is a set of sub-prompts, not a record**, and it is usually the most expensive thing in the session-start payload, so govern it by shape rather than by content. Each entry is: a heading naming the thread, **one line on where you left off**, **a pointer to the warm doc that holds the real state**, and **only the hot context that would not survive in that doc** (a branch name, a verbal commitment, a deadline, a trap). Nothing else. Before adding a line, ask *does the workstream doc already say this?* — if yes it is duplication and the pointer covers it; if the workstream doc does not say it and it matters, **write it there first, then point at it**. Never let an entry grow into a narrative of how the work went; that is WORKLOG's job, and WORKLOG is pruned precisely so it can hold that safely. **Prune on the same pass you add:** when a thread completes or goes cold, delete its block outright rather than relabelling it "superseded history" or "kept for the detail" — a block that says it is history still costs full price at every session start, because the payload loads before anything can decide to skip it. **Cap the whole section at roughly 150 lines** and re-measure occasionally; unchecked, this section is the single likeliest cause of session-start bloat, and its own preamble telling you to keep it short is demonstrably not enough. Shape guidance is what makes it stick. **Note what the warm-doc pointer is for: it is an address, not an instruction to read that doc now.** A session works one thread off this slate, so opening every candidate's workstream body at session start pays for N threads to work one — write each entry's summary line so the slate reads without opening anything, and phrase the pointer so it does not read as a session-start imperative. See `session-start.md` § *Initialization stops at the index*.

**Style:**

- Brief is fine — a few lines per entry. A terse entry beats a missing one.
- Follow any publishing rules for shared docs (see `doc-publishing.md` if present).
- Cross-reference: when DECISIONS.md captures a decision sourced from a tracker ticket or external proposal, link it.

**Triggers during a session — update on the same turn or the next:**

- A user message establishes new direction → the relevant doc gets touched
- A live API/console finding contradicts a prior assumption → INTEL.md entry now
- Creating a project or set of issues in your tracker → PLAN.md entry now
- Discovering a constraint that blocks the planned approach → INTEL.md (the finding) and possibly DECISIONS.md (the pivoted decision)
- A non-trivial doc gets written → MODEL.md or PLAN.md should reference it

**Self-check:** When work finishes, ask *did I learn a new fact, or make a new decision, that isn't yet in its proper home?* — not *did work happen?* Decision → DECISIONS.md; model shift → MODEL.md; workstream move → PLAN.md; new externally-sourced fact → INTEL.md (source named). If the only output is edits already captured in the lobes / your tracker / external docs / git, there is nothing to record — do not write a changelog into INTEL.

## Working Method

Standing guidance for how to work in this repo. Always-loaded because it applies broadly.

### Verify before asserting

- **Validate live sources before propagating a claim.** When the knowledge base, a note, or a person asserts state (counts, ticket status, doc or code content, "drafted but unfiled" claims), query the live source first before repeating it: the ticketing tool, `git`/`gh`, the API, or Read. The knowledge base is a snapshot; the live system is authoritative. Correct the snapshot and flag the delta when they disagree.
- **Verify code/system claims in the source before a decision rests on them.** Specs and write-ups describe intent; only the code / live state is ground truth, and implementations depart from spec. Open the file or hit the API; don't carry a claim on inference.
- **Pull the record before re-deriving a method or finding.** The cold docs (DECISIONS / INTEL) and any archive are on-demand, not loaded at session start; the index showing a doc exists is not the same as having read it. The record often already holds the method or the answer.
- **An explanatory comment is a CLAIM and gets code's evidentiary bar.** Run it or don't claim it. A wrong comment is worse than none, because it sits next to the code and gets trusted. This bites hardest on stacked branches: a comment describing a mechanism that lives in a *sibling* branch reads as true, and the reader has no way to tell. So **grep every claim-shaped comment for symbols that must resolve on the branch it ships in**, and where a symbol legitimately lives in a sibling or upstream, say so and name it.
- **⚠️ Before trusting a check, confirm it CAN fail.** A check whose candidate set includes its own subject cannot: grepping the tree for a symbol cited in a comment matches *the citing comment*, so every symbol resolves by construction and the sweep reports a clean zero on a tree that has the defect. Exclude the citing form from the candidate set (for the grep case, drop comment lines) and the same sweep finds real instances. The general habit: **run the check against a known-bad input first**, or mutate the thing it guards and watch it go red. Silence from a watcher is the same trap. A monitor that emits nothing looks identical to "not yet", so it is not evidence of a state.
- **Enumerate a guard's failure modes before proving it, not the ones convenient to reproduce.** Proving some of them and calling the guard proven is its own defect, and the mode left unproved is reliably the one that fails worst: the case that *hangs* or *goes quiet* rather than erroring, because it produces no signal to notice. Unbounded calls are the classic example (a liveness probe with no timeout blocks forever, so CI kills the job and it reads as slow CI rather than as a check that never ran). A useful tell needs no domain knowledge: **when a new call is inconsistent with its established neighbour** (the neighbour has a timeout / retry / error branch and yours does not), treat that as a coverage question, not a style one. The unifying failure across all of this is **absence of a signal read as success**, so before trusting any detector ask what it emits when the thing it watches breaks in the way you have not tested. If the answer is "nothing", that is the bug.

### Team-facing writing

- **No LOC, time, or t-shirt estimates in shared / architecture docs.** They invite false precision and date poorly. Describe complexity qualitatively (what it owns, what's native, what coherence costs exist). Naming an API surface is structural and fine; counting is not. Spike logs may keep raw measurements; shared docs may not.
- **State the current required shape as fact.** In tickets, comments, and docs, describe what's needed now; don't narrate the journey in a pile of decision-comments. Break a broad item into per-unit subitems. Same applies to your own responses: concise, not stream-of-consciousness.
- **Natural voice in all external comms** (PR/MR comments, chat, email, not just published docs). No em-dashes anywhere. Strip AI tells (not-just-X-but-Y, rule-of-three triads, both-sides cadence, summarizing kickers, filler). This extends `doc-publishing.md` §8 beyond docs to anything sent to a named recipient.
- **Annotate every PR / MR number with its title, same rule and same reasons as ticket IDs.** A bare `#123` carries no meaning, and a reviewer is often asked about a change they have not opened. Use `#123 (short title)`, or a link whose whole label is `#123 — short title` where links render. Three things specific to change requests: **name the repo** unless context makes it unambiguous, because numbers are per-repo and in a multi-repo workspace `#123` could be any of them (a wrong-repo link is worse than a bare number, since it looks authoritative and lands somewhere unrelated); **strip the conventional-commit prefix** from the cited title, keeping the human clause, since the prefix is machine metadata and is also the *volatile* half (retitles typically change the prefix and leave the clause, so a stripped annotation survives them); and **verify the title with the forge CLI** rather than recalling it, since titles change after review.
- **Annotate every ticket ID with its title.** Whenever you cite a ticket ID in any output — chat responses, docs, PR/MR/chat comments, plan or task notes, the decision record — append the ticket title in parens on first mention (`PROJ-123 (short title here)`), or a short summary if the title is long. Bare ID is fine for repeat mentions within the same response/doc. People tracking many tickets can't map a bare ID from memory. Use the title you already know from context; when unsure, verify it against the live ticketing tool rather than guessing — a wrong annotation is worse than none.

### Scope and ownership

- **Surface process / ownership gaps as ownership problems; don't absorb them.** When a process or onboarding gap surfaces (no CONTRIBUTING.md, an undocumented paved path), name *who should own it* rather than quietly drafting the artifact yourself. Absorbing other people's deliverables perpetuates the gap. Capturing the gap in QUESTIONS / PLAN and naming the likely owner is fine.
